# Homepage repository instructions

These instructions apply to the entire repository. Follow the additional rules
below whenever creating, revising, compiling, or listing a paper for the
Repository page.

## Purpose and scope

- The Repository is a personal collection of fully AI-generated papers that are
  not intended for submission.
- Treat every paper as a rigorous mathematical manuscript, not as a casual note.
  The target is arXiv-ready writing, typesetting, citations, and proof quality.
- Never trade correctness for completing the requested theorem. If a claimed
  extension is not justified, identify the obstruction and stop short of
  claiming it.

## Research and mathematical verification

- Read every specifically referenced paper in full when its proof is being
  adapted. Prefer the PDF or TeX source and primary sources.
- Reconstruct the proof dependency-by-dependency. Explicitly identify which
  lemmas generalize, which require replacement, and which conclusions are only
  existential or algorithmic.
- Check kernels, quotient spaces, effective dimensions, zero cases, parameter
  ranges, endpoint cases, constants hidden by asymptotic notation, and the exact
  strength of each application.
- Use independent mathematical audits or subagents for substantial papers when
  available. Ask them to search for counterexamples and hidden assumptions, not
  merely to polish prose.
- Cite primary sources for imported theorems. Do not invent bibliographic data,
  theorem numbers, algorithms, or novelty claims.
- Keep limitations explicit. For example, do not turn an existential argument
  into a polynomial-time result, a cut sparsifier into a spectral sparsifier, or
  a symmetric statement into an asymmetric one.

## Writing and paper format

- Match the restrained, math-first style of the papers listed on
  research.html. For this topic, use "Sparsifying sums of norms" as the closest
  organization and prose reference.
- State the mathematical setup and main guarantee immediately. Use direct prose,
  precise theorem statements, punctuated displays, and a substantive proof
  overview.
- Each abstract must include:
  1. the main result and its assumptions,
  2. the principal applications, and
  3. only a very high-level sketch of the proof.
- Do not add a separate "Informal description" field to repository.html.
- Repository papers have no named author unless the user explicitly requests
  one. A date is allowed and must use Month Day, Year.
- Put an accurate AI-generation note immediately below the abstract. Format the
  label as boldface `Note.` and set the disclosure itself in normal roman text,
  not italics. State the actual model and harness; never reuse a model or
  harness name if it would be false. State who prompted the paper, and use
  "prompted by Yang Liu" only when that attribution is accurate.
- For repo/sparsifying-sums-seminorms/paper.tex, preserve the exact disclosure
  text after the bold `Note.` label: "This paper was fully AI generated by GPT
  5.6 Sol and the Devin harness, prompted by Yang Liu."

## Files and compilation

- Store each paper in a descriptive nested folder: repo/<paper-slug>/.
- Retain the final:
  - paper.pdf
  - paper.tex
  - paper.bbl
  - references.bib when BibTeX is used
  - a short build README.md when useful
- Do not retain LaTeX or review artifacts such as .aux, .blg, .log, .out,
  temporary downloads, extracted source archives, or preview images.
- Compile from a clean state. With BibTeX, use:

      pdflatex paper.tex
      bibtex paper
      pdflatex paper.tex
      pdflatex paper.tex

- Require a successful build with resolved references and no LaTeX warnings,
  overfull boxes, undefined citations, or missing links.
- Visually inspect at least the first page and representative theorem,
  application, and bibliography pages. Verify the final PDF text contains the
  date and disclosure and contains no unintended author.

## Repository page integration

- Keep repository.html visually consistent with index.html, research.html, and
  teaching.html; use the existing Bootstrap font and navigation conventions.
- List papers as numbered entries with a title, working PDF link, and the
  existing native expansion arrow.
- Treat the original-addition provenance link as the paper's timestamp. Put it
  beside the PDF link in the collapsed entry header, label it
  `Added Month Day, Year`, and keep the expanded content abstract-only.
- Point the timestamp to the canonical GitHub pull request that first added the
  paper to repository.html. If the paper was added by a direct commit, use an
  immutable full-SHA commit URL instead. Derive the displayed date from the PR
  merge date or direct commit date, respectively. Never replace this link or
  date when the paper is revised; later version history may be recorded
  separately if requested.
- For repo/sparsifying-sums-seminorms/, preserve the timestamp
  `Added July 12, 2026` and link it to commit
  `8efe41f9e87f41d17bef7a43204d8f4a8d6da7c2` in this repository.
- The expanded content contains only an abstract. Base it closely on the actual
  paper abstract and ensure it states results, applications, and a very
  high-level proof sketch.
- Store PDF links under repo/...; verify every relative target exists.
- Remove dummy entries once a real paper is available.
- Preserve user-written Repository introductory text unless explicitly asked to
  edit it.
- Check balanced HTML tags, responsive behavior, local links, and
  git diff --check.

## Git hygiene

- Preserve unrelated user changes.
- Do not commit or push unless the user explicitly asks.
- Before committing, review the complete diff and include only intended source,
  PDF, bibliography, page, and instruction files.
